# 矿山数字孪生 AI Agent —— 选型与架构决策报告

> 状态：初始选型阶段（v0.1 讨论稿）
> 场景：本地 AI 服务器私有化部署，服务于 Unity 开发的矿山数字孪生项目
> 调研时间基准：2026 年

---

## 一、结论先行

**不要从 0 到 1 造 Agent 框架，也不要纯粹"拼装开源"。正确姿势是：复用骨架 + 自研灵魂。**

具体说：

| 层次 | 决策 | 理由 |
|---|---|---|
| 通用编排框架 | **复用**（LangGraph 为主） | 2026 年这块已高度成熟，自研等于重造轮子且必然更差 |
| 工具协议层 | **复用**（MCP 标准） | Unity 官方 + 社区已全面拥抱 MCP，事实标准已形成 |
| Unity 桥接层 | **复用**（MIT 开源项目打底 + 自研领域工具） | 通用工具白嫖，矿山专用工具必须自研 |
| 矿山领域语义层 | **自研**（本体/规则/工具/安全校验） | 这才是唯一的护城河，通用框架给不了 |
| 知识库/RAG | **复用**（RAGFlow 或自建向量库） | 文档解析已成熟，但矿山语料要自己清洗 |
| 模型层 | **复用开源模型 + 领域微调** | 本地部署 Qwen3/DeepSeek，用矿山数据做 SFT/蒸馏 |

一句话：**80% 复用成熟开源，20% 自研领域层。那 20% 决定了项目成败。**

## 二、先澄清一个关键歧义

"支持整个 Unity 开发的数字孪生项目的 AI Agent"，实际上包含**两类完全不同**的 Agent。它们的架构、技术栈、风险等级都不一样，必须先分开：

### A 类：开发期 Agent（Dev-time）
- **面向谁**：你们的 Unity 开发团队
- **干什么**：在 Unity Editor 里自动建场景、写 C#、挂组件、读 Console 修报错、跑测试、做资源管理
- **典型交互**：在 Cline / Claude Code / Cursor 里说"把皮带输送机的脚本挂到 Conveyor_01 上并配置好参数"
- **技术形态**：MCP Client（IDE） ↔ MCP Server（Unity 插件）
- **风险**：低。改坏了可以回滚，不涉及生产安全

### B 类：运行期 Agent（Run-time）
- **面向谁**：矿山调度员、安全员、设备工程师
- **干什么**：全域监控、理解式执行（一句话生成调度指令）、事前预测（设备故障/堆场拥堵/产量趋势）
- **典型交互**：调度员说"把 3 号破碎站的处理量提到 1200 吨/小时"，系统自动核对状态 → 安全校验 → 生成可执行指令 → 高风险操作人工确认
- **技术形态**：Agent 服务 ↔ 数字孪生运行时 ↔ 真实生产系统（PLC / 安全监测 / 人员定位）
- **风险**：**高**。指令下发到真实设备，涉及人员安全与生产安全

> **关键判断**：A 类可以"拿来主义"快速见效；B 类必须自研领域层 + 强安全约束，不能纯靠 LLM。
> 两类可以**共享同一个领域知识层和 MCP 工具层**，这是架构设计上最大的复用点。

## 三、行业现状调研（2025-2026）

### 3.1 政策与行业背景

- **《金属非金属矿山智能化建设指南（2025年版）》**（矿安综〔2025〕20号，国家矿山安全监察局，2025-12-11 印发）已正式发布，明确要求"一矿一策""分类分级""需求导向+适度超前"，并建立智能化等级评价体系。
- 这意味着：**矿山智能化已从"要不要做"变成"怎么做、怎么评级"**。AI Agent 作为智能化等级的一部分，有明确的政策驱动和验收需求。

### 3.2 矿山行业已有的垂域 Agent 实践（重要参考）

**① 希迪智驾"小元"——全球首个矿山智能体（2026-09 发布，已在 15 个矿山落地）**

其三层架构极具参考价值：

| 小元的层 | 职责 | 对应的通用技术 |
|---|---|---|
| **"元神"矿山大模型** | 理解意图、任务推理、计划生成 | 领域微调 LLM |
| **Harness 智能体编排引擎** | 把复杂目标拆解为可执行任务链 | Agent 编排框架 |
| **重载世界模型** | 端云协同做物理推演 | 数字孪生 + 仿真 |

实战效果：批量调度从数分钟 → 3 秒；生产报告从大半天 → 3 分钟；故障处理效率 +80%；单位运输成本 -5%；单车运输效率 +11.7%。

**关键设计**：数据留存矿区内网；调度指令全程留痕；只有高风险操作才需人工确认。

**② 云鼎科技（山东能源）—— 垂域矿山大模型 + NLP 应用智能体**

- 用 DeepSeek-R1 作教师模型，对百万级矿山高质量数据（安全生产、设备管理、应急救援）做**数据蒸馏**，得到矿山 COT 数据，再微调自有小模型
- 结果：安全生产知识问答准确率 **96%+**，中文检索精度 **90%+**（自研端到端 RAG + 中文增强 Embedding + Reranker + 混合检索）
- 应用智能体：知识管理、工作流编排、应用构建、知识运营
- **明确强调"本地部署"**：针对矿山/化工/电力等行业对数据安全和私有化部署的强需求

> **这两家的共同点，就是本报告的核心结论**：都是**通用能力复用 + 领域数据自研**，没有一个是从 0 造框架。

### 3.3 Unity 侧的能力现状（好消息）

**① Unity 官方 MCP Server（2026-05 开放 beta）**
- Unity 6 起官方提供 MCP Server，Claude Code / Cursor / Windsurf / VS Code Copilot 等可直接连接 Unity Editor
- 支持：读取场景层级、读 Console、编辑脚本、触发 Editor 动作、检查缺失组件
- 最实用的闭环：**Agent 读 Console 报错 → 定位脚本 → 写修复 → 再读 Console 验证**，全程无需人工复制粘贴

**② realvirtual.io MCP Server（MIT 开源，工业数字孪生方向）**
- 免费开源的 Unity 包，实现 MCP 协议，让 AI Agent 控制 Unity Editor **以及活着的数字孪生**
- 能力：启动仿真、驱动输送机、读传感器、解机器人逆运动学
- 扩展方式极简：给任意 `static` C# 方法加 `[McpTool]` 特性，重新编译即可，**无需写 Python、无需手动注册**
- 配套 realvirtual Digital Twin Starter（免费）

**③ CoplayDev/unity-mcp（MIT 开源，社区最活跃）**
- **48 个 MCP 工具入口**，覆盖资产/场景/脚本/测试/性能/构建
- 兼容 Unity 2021.3 LTS → 6.x
- 支持任意 MCP 客户端：Claude Desktop & Code、Cursor、VS Code、Windsurf、**Cline**、Gemini CLI
- 有 Roslyn 脚本校验、多 Unity 实例路由、远程托管服务+鉴权等进阶能力

> **结论**：Unity + MCP 的生态在 2026 年已经**足够成熟**。A 类（开发期）Agent 完全可以**几小时内跑通**，零自研成本。

## 四、框架选型对比

### 4.1 许可证是最大的坑（务必先看这个）

| 框架 | 许可证 | 商用限制 | 私有化部署 | 对外做产品/多租户的风险 |
|---|---|---|---|---|
| **LangGraph** | MIT | 无 | ✅ | ✅ 无风险 |
| **Coze Studio** | Apache-2.0 | 无（仅限商标） | ✅ | ✅ 无风险 |
| **RAGFlow** | Apache-2.0 | 无 | ✅ | ✅ 无风险 |
| **Dify** | Dify OSL（Apache-2.0 + 附加条款） | ⚠️ 禁止多租户 SaaS；**不得去除 logo** | ✅ | ⚠️ **有风险** |
| **n8n** | Sustainable Use License（fair-code） | ⚠️ 禁止对外商业化 SaaS | ✅ | ⚠️ **有风险**，严格说不算开源 |

> **决策影响**：如果未来要把这套 Agent 作为**产品对外交付 / 多租户运营**（矿山行业 SaaS 是很可能的商业模式），**Dify 和 n8n 会有法律风险**。
> 建议：核心链路用 **MIT / Apache-2.0** 组件（LangGraph + RAGFlow + Coze Studio），Dify / n8n 只在**内部自用**场景引入。

### 4.2 能力对比

| 维度 | Dify | Coze Studio | RAGFlow | n8n | LangGraph |
|---|---|---|---|---|---|
| 定位 | LLM 应用平台 | Agent 开发平台 | 深度文档 RAG 引擎 | 工作流自动化 | **代码优先编排框架** |
| 形态 | 低代码可视化 | 低代码可视化 | 专用服务 | 低代码可视化 | **纯代码（Python）** |
| Agent 能力 | ★★★★ | ★★★★ | ★★★ | ★★★★ | ★★★★★ |
| RAG 能力 | ★★★★ | ★★ | ★★★★★ | ★★ | ★★★（需自建） |
| 集成数量 | 中 | 中 | 中 | 400+（最多） | 无（自己写） |
| 代码灵活性 | 高 | 低 | 中 | 高 | **最高** |
| 可控性 / 可调试 | 中 | 中 | 中 | 中 | **最高** |
| 适合团队 | 初中级 | 非技术 | 初中级 | 中高级 | **中高级** |
| Human-in-the-loop | 弱 | 弱 | 弱 | 中 | **★★★★★（interrupt 原生）** |
| 状态持久化 / 断点恢复 | 中 | 中 | 弱 | 中 | **★★★★★** |

### 4.3 为什么编排层选 LangGraph 而不是低代码平台

矿山运行期 Agent 有三个硬需求，低代码平台天然吃亏：

1. **强安全约束 / 人在回路**
   高风险指令必须中断等待人工确认。LangGraph 的 `interrupt` + checkpoint 机制是原生支持；Dify / Coze 的 HITL 很弱。
2. **确定性要求**
   调度指令不能"看起来差不多"。需要 LLM 推理 + **规则引擎**混合编排，必须能精确控制每一步走哪条分支。可视化平台会限制你。
3. **长流程 + 可恢复**
   "查状态 → 核对参数 → 安全校验 → 生成指令 → 下发 → 回执"是多步长流程，中途可能等人工几十分钟。需要状态持久化和断点恢复。

> 但**低代码平台不是没用**：Dify / Coze Studio 适合做**知识问答类**、**内部工具类**应用，交付快，让业务同学自己配。
> 建议**双栈**：LangGraph 跑核心业务链路，Coze Studio（Apache-2.0）跑边缘轻应用 + 做评估监控。

### 5.2 关于"从 0 到 1"的边界划定

| 组件 | 决策 | 说明 |

| Unity 通用工具（48 个） | ❌ 不自研 | 用 CoplayDev/unity-mcp |
| 文档解析 / 向量检索 | ❌ 不自研 | 用 RAGFlow 或 Milvus |
| 推理服务 | ❌ 不自研 | 用 vLLM / SGLang |

| **矿山工艺与安全规则库** | ✅ **自研** | 可执行的规则，不是文档 |

| **评测集与回归测试** | ✅ **自研** | 没有评测就没有可信度 |


### 5.3 本地 AI 服务器技术栈建议

| 项 | 推荐 | 备选 | 理由 |
|---|---|---|---|
| 推理引擎 | **vLLM** | SGLang | 生态最好、OpenAI 协议兼容、tool calling 支持成熟 |
| 主力模型 | **Qwen3 系列**（32B 级） | GLM-4 / DeepSeek-V3 | 中文强、工具调用稳、可微调、可本地部署 |
| 推理模型 | **DeepSeek-R1-Distill** | — | 复杂故障诊断 / 规划场景 |
| 向量模型 | **BGE-M3** | — | 中文 + 多语言 + 长文本，社区验证充分 |
| 重排模型 | **BGE-Reranker** | — | 云鼎科技同款路线 |
| 向量库 | **Milvus** 或 **pgvector** | Elasticsearch | Milvus 规模好；pgvector 运维简单 |
| 编排 | **LangGraph**（MIT） | — | 见 4.3 |
| 可观测 | **Langfuse** | Coze Loop | 链路追踪 + 评测 |

> **算力提示**：32B 模型 FP16 约需 64GB 显存；AWQ / GPTQ 4bit 量化后约 20GB，单张 A100 / H800 或双 4090 可跑。
> 建议先按 **Qwen3-14B / 32B 量化版**起步，验证链路后再决定是否上更大模型或做蒸馏小模型。

### 5.4 Unity 双向集成路径

**方向一：Agent → Unity（控制数字孪生）**

复用 `realvirtual.io MCP Server` 的 `[McpTool]` 模式，自研矿山工具：

```csharp
// 自研矿山领域工具示例（编译即注册，Agent 立即可见）
[McpTool("查询指定设备当前运行状态")]
public static EquipmentState GetEquipmentState(string equipmentId) { ... }

[McpTool("驱动皮带输送机，返回安全校验结果")]
public static SafetyCheckResult DriveConveyor(string id, float speed) { ... }

[McpTool("读取指定测点的实时传感器数值")]
public static SensorReading ReadSensor(string sensorId) { ... }

[McpTool("按标高/坐标查询地质模型切片")]
public static GeologySlice QueryGeology(float elevation) { ... }

[McpTool("预测指定设备未来 N 小时的故障概率")]
public static FailurePrediction PredictFailure(string equipmentId, int hours) { ... }
```

**方向二：Unity → Agent（孪生状态上报）**

孪生运行时把场景状态（设备位姿、物料流量、告警、人员位置）通过 MCP Resource 或事件流推给 Agent，作为推理上下文。

> **关键设计原则**：所有"写"操作（控制类工具）必须走安全校验引擎，且高风险操作返回 `requireConfirmation: true` 触发 LangGraph 的 `interrupt`。

## 七、分阶段路线图

### Phase 0：验证（2-4 周）— 目标：跑通闭环，零风险
- [ ] 本地 AI 服务器部署 **vLLM + Qwen3**（OpenAI 兼容 API）
- [ ] Unity 工程接入 **CoplayDev/unity-mcp**，用 Cline 直连 Unity Editor
- [ ] 验证场景：让 Agent 读 Console 报错并自动修复
- [ ] **产出**：开发期 Agent 可用，团队效率立刻提升
- **风险**：极低。这一步就能交付价值。

### Phase 1：孪生工具化（1-2 月）— 目标：Agent 能"看见"孪生
- [ ] 引入 **realvirtual.io MCP Server** 或自建 Unity MCP Server
- [ ] 定义并实现第一批**矿山领域 MCP 工具**（只读为主）：设备状态、传感器、地质查询、告警列表
- [ ] 建立**矿山本体 v0.1**（设备 / 区域 / 工序 / 告警的实体与关系）
- [ ] 搭建 **RAGFlow + BGE-M3** 知识库，灌入安全规程 / 设备手册 / 应急预案
- [ ] **产出**：能问"3 号皮带现在什么状态？""这个故障按规程怎么处理？"
- **风险**：低。只读操作，不涉及控制。

### Phase 2：编排与安全（2-3 月）— 目标：能"理解式执行"
- [ ] 用 **LangGraph** 搭建核心编排：意图理解 → 任务拆解 → 工具调用 → 结果汇总
- [ ] 实现**安全校验引擎**：所有写操作前置校验，高风险触发 `interrupt` 等人工确认
- [ ] 实现**指令留痕 + 审计追溯**
- [ ] 建**评测集**（矿山场景问答 + 指令生成准确率），建立回归测试
- [ ] **产出**：调度类指令可用，但限定在低风险场景
- **风险**：中。开始涉及写操作，必须严格限制范围。

### Phase 3：领域深化（3-6 月）— 目标：形成壁垒
- [ ] **矿山语料清洗 + 数据蒸馏**，微调领域小模型（参考云鼎科技路线）
- [ ] 建**工艺规则库**（可执行规则，非文档）
- [ ] **事前预测**：设备故障、堆场拥堵、产量趋势
- [ ] 多 Agent 协同（调度 Agent / 安全 Agent / 设备 Agent）
- [ ] 完善评测与可观测（Langfuse / Coze Loop）
- **产出**：可复制的系统能力，具备跨矿山推广条件
- **风险**：中高。需要数据积累和持续调优。

## 八、主要风险与决策点

| # | 风险 | 应对 |
|---|---|---|
| 1 | **LLM 幻觉导致错误指令** | 规则引擎兜底 + 安全校验引擎 + 高风险人工确认；LLM 只做理解与建议，不做最终放行 |
| 2 | **数据不出域与本地算力不足** | 优先量化部署（4bit）；分阶段扩容；知识库与模型都本地化 |
| 3 | **许可证风险（Dify / n8n）** | 核心链路只用 MIT / Apache-2.0；Dify / n8n 仅内部自用 |
| 4 | **开源项目停更 / 变更** | MCP 是开放标准，Unity 侧工具可自研替代；关键组件做抽象层隔离 |
| 5 | **矿山术语 / 方言导致理解偏差** | 建术语词典与同义词归一化层，持续迭代 |
| 6 | **缺少评测导致效果无法证明** | Phase 2 就建评测集，用数据说话（对标云鼎 96% 问答准确率） |
| 7 | **Unity 版本与插件兼容** | unity-mcp 支持 2021.3 LTS → 6.x；建议统一到 Unity 6 LTS |

## 九、待确认的关键问题

在进入详细设计前，需要业务方明确：

1. **主场景是 A 类（开发期）还是 B 类（运行期）？** 两者优先级决定 Phase 0 的投入方向。
2. **本地 AI 服务器的具体配置？**（GPU 型号 / 数量 / 显存）决定模型规模选型。
3. **是否需要对外交付 / 多租户？** 决定许可证策略。
4. **目标矿种与开采方式？**（露天 / 井工；煤 / 金属 / 非金属）决定领域层建模范围。
5. **需要对接的现有系统清单？**（安全监测、人员定位、PLC、MES、地测采）
6. **是否有历史数据可用于微调？**（工单、规程、报告、日志）决定 Phase 3 可行性。
